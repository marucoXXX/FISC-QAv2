# FISC-QAv2 エージェント解説ガイド

このドキュメントでは、FISC-QAv2 システムを構成する5つのエージェント（Agent 0〜4）について、技術的背景の異なる読者が理解できるように解説します。

> **対象読者**: 中学生〜エンジニアまで。各エージェントのセクションは「やさしい解説」→「なぜ必要か」→「代替手段」の3パート構成です。

---

## 1. システム全体像

### このシステムは何をするの？

銀行や証券会社などの金融機関は、「セキュリティ対策をちゃんとやっていますか？」というアンケート（質問票）に毎年回答する必要があります。質問は数十〜数百問あり、社内のいろいろな資料を調べて回答しなければなりません。

このシステムは、**5人の専門チームが協力して質問票に自動回答する仕組み**です。

| チームメンバー | 役割 | 人間で例えると |
|---|---|---|
| **Orchestrator（司令塔）** | 全体の段取りを決めて指示を出す | プロジェクトマネージャー |
| **Indexer（資料整理係）** | 社内資料の目録を作る | 図書館の司書 |
| **Router（振り分け係）** | 質問ごとに「どの資料を読めばいいか」を決める | ベテラン社員 |
| **Reader（回答担当）** | 実際に資料を読んで回答を書く | 新人〜中堅社員（複数人） |
| **Reviewer（チェック係）** | 全員の回答をまとめてチェックする | 上司・品質管理担当 |

### パイプライン図

```
質問票(Excel)
    │
    ▼
┌──────────────────────────────────────────────────┐
│  Orchestrator（司令塔）                            │
│                                                    │
│  ① 質問票を読み込む                                │
│  ② Indexer に資料の目録を作らせる                   │
│  ③ Router に「誰がどの資料を読むか」決めさせる       │
│  ④ 過去の回答が使えるものは再利用（②の更新情報 + ③のルーティング結果を使って判断）│
│  ⑤ Reader たちに並列で回答を書かせる                 │
│  ⑥ Reviewer に全回答をチェックさせる                 │
│  ⑦ 結果を Excel に書き出す                          │
└──────────────────────────────────────────────────┘
    │
    ▼
出力Excel + レビューノート
```

## 2. Agent 0: Orchestrator（司令塔）

> **ソースコード**: `src/orchestrator.py`

### パート A: やさしい解説

学校の文化祭で、クラスの出し物を準備するところを想像してください。Orchestrator は**実行委員長**です。

- 「まず準備物を確認して」「次にチラシを作って」「最後にリハーサルして」と、やるべきことの順番を決めて、みんなに指示を出します
- 回答担当（Reader）が複数人いるときは、**同時に作業させて時間を短縮**します（例: 3人のReaderが同時に別々の質問に取り組む）
- 誰かが失敗したら、**もう一度やり直しさせます**（最大3回まで）
- Indexer に「この資料は去年から変わった？」と確認し、Router に「この質問にはどの資料が関係する？」と聞いたあとで、「関係する資料が全部変わっていないなら、去年の回答をそのまま使おう」と判断します

Orchestrator 自身は AI（LLM）を使いません。純粋に「段取り」と「管理」だけを担当します。

### パート B: なぜ必要か

**Orchestrator がいなくなったら？**

- **実行順序が崩壊する**: Indexer が終わる前に Router が動いてしまい、資料の情報がない状態でルーティングすることになる
- **並列実行ができない**: Reader を1人ずつ順番に実行するしかなく、20問あれば20回直列に API を呼ぶことになり、処理時間が大幅に増加する
- **リトライがない**: LLM API は一時的に失敗することがある。リトライ機構がなければ、1回の失敗で回答が「未回答」になってしまう
- **過去回答の再利用ができない**: 毎回すべての質問を LLM に投げることになり、コストと時間が無駄になる
- **結果の集約が散逸する**: 各 Reader の結果を誰がマージするのか不明になる

### パート C: 代替手段

| 方式 | 概要 | メリット | デメリット |
|------|------|----------|------------|
| **現在の方式: Orchestrator** | 専用モジュールがパイプライン全体を制御。ThreadPoolExecutor で Reader を並列実行 | 並列実行・リトライ・過去回答再利用を一元管理。各エージェントは疎結合を維持 | Orchestrator 自体のコードが複雑になりやすい |
| **代替①: シェルスクリプトで直列実行** | `index.py → route.py → read.py → review.py` をシェルから順に呼ぶ | 実装が極めてシンプル。デバッグしやすい | 並列実行不可。リトライは自前実装が必要。過去回答の再利用判定の置き場がない |
| **代替②: 手動で順番に実行** | ユーザーが CLI で各コマンドを順に叩く | 各ステップの結果を確認しながら進められる | 人間の手間がかかる。自動化の意味がなくなる |

## 3. Agent 1: Indexer（資料整理係）

> **ソースコード**: `src/indexer.py`

### パート A: やさしい解説

図書館に行ったとき、本棚に直接行って1冊ずつ探すのは大変ですよね。でも**図書カード（目録）**があれば、「この本はどの棚にあって、どんな内容か」がすぐにわかります。

Indexer は**図書館の司書**です。

- 社内の資料フォルダ（KB）にあるすべてのファイル（PDF、Word、Excelなど）を1つずつ開いて、**中身のダイジェスト（500文字の要約）**を作ります
- 各ファイルが**どれくらいの分量か**（トークン数）を見積もります
- 前回からファイルが**更新されたかどうか**もチェックします（ファイルの更新日時を比較）

具体的には:
- PDF → 先頭2ページからテキストを取り出す
- Word → 見出しを優先的に抜き出す（目次はスキップ）
- Excel → 全行を読む
- テキストファイル → 先頭50行を読む

### パート B: なぜ必要か

**Indexer がいなくなったら？**

- **Router が判断材料を失う**: Router は「どのファイルにどんな内容が書いてあるか」を知らないと、質問に合ったファイルを選べない。ファイル名だけでは `dr_bcp_plan.pdf` が何の資料かわからない
- **トークン予算の計算ができない**: 各ファイルのトークン数がわからないと、Reader に渡すファイルの組み合わせが LLM のトークン上限を超えてしまう可能性がある
- **過去回答の再利用判定ができない**: ファイルの更新検知ができないため、去年と同じ回答が使えるかどうか判断できない
- **全ファイルを Router に丸投げ**: Router が全ファイルの全文を読むことになり、トークンコストが爆発する

### パート C: 代替手段

| 方式 | 概要 | メリット | デメリット |
|------|------|----------|------------|
| **現在の方式: Indexer** | 全ファイルを走査し、要約・トークン数推定・更新検知を行う。オプションで LLM 要約も可能 | Router に十分な判断材料を提供。更新検知で過去回答再利用も支援 | 初回走査に時間がかかる（ファイル数に比例） |
| **代替①: ファイル名だけでルーティング** | ファイルの中身を読まず、ファイル名とフォルダ構造だけで Router に渡す | 走査不要で高速 | ファイル名が不明瞭だと誤ルーティング。トークン推定不可。更新検知不可 |
| **代替②: 全ファイルを Router に渡す** | Indexer を飛ばして、Router が全ファイルの全文を直接読む | 中間ステップが不要 | Router の入力トークンが爆発（KB 全体で数十万トークンになりうる）。コスト・速度ともに非現実的 |
| **代替③: ベクトルDB（RAG）** | ファイルをチャンク分割してベクトル化し、質問との類似度検索でファイルを選定 | 大規模 KB でもスケールする。意味的な検索が可能 | インフラ追加が必要（ベクトルDB）。チャンク分割の品質がルーティング精度に直結 |

## 4. Agent 2: Router（振り分け係）

> **ソースコード**: `src/router.py`

### パート A: やさしい解説

テストで「問題に関係ある教科書のページだけを読む」のと、「教科書を全部読む」のでは、効率がまったく違いますよね。

Router は**ベテランの先輩社員**です。質問を見て、「この質問に答えるには、あの資料とこの資料を読めばいい」と判断してくれます。

**2つのやり方**があります:
1. **AI（LLM）に聞く方法**: 質問の内容と資料の要約を LLM に渡して、「どの資料が関係ありそう？」と判断してもらう
2. **キーワードで自動判定する方法（フォールバック）**: 質問の大分類（「アクセス管理」「インシデント対応」など）に対して、あらかじめ決めたキーワードテーブルで資料を選ぶ

AI が使えないときや、AI の回答がおかしかったときは、自動的にキーワード方式に切り替わります。

さらに Router は**荷物の詰め方（ビンパッキング）**も担当します。1人の Reader が読める分量（80,000トークン）に収まるように、質問とファイルを Reader A、Reader B、Reader C…に振り分けます。

### パート B: なぜ必要か

**Router がいなくなったら？**

- **トークンコストが爆発する**: 20問 × 12ファイルの全組み合わせを Reader に渡すと、1回の実行で数百万トークンを消費する可能性がある。Router があれば、各質問に1〜3ファイルだけ割り当てるので大幅に削減できる
- **回答精度が下がる**: Reader に関係のないファイルまで渡すと、LLM が無関係な情報に引きずられて的外れな回答を生成するリスクがある
- **Reader の分割ができない**: トークン予算に基づく Reader の分割がないと、1つの Reader にすべてを詰め込んでトークン上限を超えるか、非効率な分割になる

### パート C: 代替手段

| 方式 | 概要 | メリット | デメリット |
|------|------|----------|------------|
| **現在の方式: LLM動的ルーティング + 静的フォールバック** | LLM が質問と資料要約を見て最適なファイルを選定。失敗時はキーワードテーブル（`_KEYWORD_MAP`: 12カテゴリ）にフォールバック | 質問の意味を理解した高精度なルーティング。フォールバックで堅牢性も確保 | LLM 呼び出し1回分のコスト（2,048トークン）が追加 |
| **代替①: 全ファイルを全 Reader に渡す** | ルーティングなしで、すべてのファイルをすべての Reader に読ませる | ルーティングミスが発生しない（網羅性100%） | トークンコストが数十倍に膨張。Reader のコンテキスト窓に収まらない可能性大 |
| **代替②: 固定テーブルのみ** | LLM を使わず、`_KEYWORD_MAP` のキーワードマッチングだけで割り当て | LLM コストゼロ。動作が決定論的で予測可能 | 新しいカテゴリの質問に対応できない。キーワードが合わない質問は誤ルーティングされる |
| **代替③: ベクトル類似度検索** | 質問と資料チャンクのベクトル類似度で上位 N 件を選定 | 意味的な類似度で選べる。大規模 KB にスケール | 埋め込みモデルの追加コスト。チャンク粒度の調整が必要 |

## 5. Agent 3: Reader（回答担当）

> **ソースコード**: `src/reader.py`

### パート A: やさしい解説

テストで問題に答えるとき、**実際に教科書を読んで答えを書く人**が必要ですよね。Reader はまさにその役割です。

Reader は**回答を書く担当者**です。システムの中で**最も重要な存在**で、この人がいないとシステムは成り立ちません。

Reader がやることは:
1. Router から「この質問に答えるにはこのファイルを読んで」と指示を受ける
2. 指定されたファイル（PDF、Word、Excelなど）を**全文読み込む**
3. AI（LLM）に「この資料の内容をもとに、この質問に答えて」と依頼する
4. AI の回答を整理して返す（回答文、根拠、確信度など）

Reader は**複数人が同時に働けます**。例えば Reader A は質問1〜7を、Reader B は質問8〜14を、Reader C は質問15〜20を担当する、というように並列で動きます。

AI の回答がうまく読み取れなかった場合のために、**3段階のフォールバック**があります:
1. まず JSON としてそのまま読む
2. ダメならコードブロック（```json ... ```）の中身を探す
3. それでもダメなら括弧の対応を数えて JSON 部分を見つける

### パート B: なぜ必要か

**Reader がいなくなったら？**

- **回答が生成できない**: Reader は LLM を使って回答を生成する、システムの**核心部分**です。Reader なしではシステムの存在意義がなくなります
- **KB を読む手段がない**: PDF、DOCX、XLSX など複数形式のファイルを読み取る機能は Reader が担っています
- **人間が全問手作業で回答するしかない**: 数十〜数百問の質問に対して、毎回人間が資料を読んで回答を書くことになります

### パート C: 代替手段

| 方式 | 概要 | メリット | デメリット |
|------|------|----------|------------|
| **現在の方式: KB全文読み込み + LLM回答生成** | 割り当てファイルの全文を読み込み、LLM（`litellm.completion()`、max_tokens=16,384）で回答 JSON を生成 | ファイル全体を文脈として使えるため、回答精度が高い。複数質問をまとめて処理できる | トークンコストが高い。ファイルが大きいとコンテキスト窓の制約を受ける |
| **代替①: RAG（検索拡張生成）** | ファイルをチャンク分割し、質問に関連するチャンクだけを取得して LLM に渡す | トークン消費を大幅に削減。大きなファイルでも対応可能 | チャンク分割の品質に依存。文脈が断片的になり、回答精度が下がるリスク |
| **代替②: 人間が回答** | システムを使わず、人間が資料を読んで回答を書く | 最も正確（専門家が回答する場合） | 時間とコストが膨大。数百問の質問票を毎年回答するのは非現実的 |

> **注**: Reader はシステムの核心であり、LLM による回答生成を完全に代替する手段はありません。RAG は将来の改善案として有力ですが、現時点では全文読み込み方式を採用しています。

## 6. Agent 4: Reviewer（チェック係）

> **ソースコード**: `src/reviewer.py`

### パート A: やさしい解説

テストの答案を書いたあと、**先生が採点する**ステップを想像してください。Reviewer は**上司や品質管理の担当者**です。

Reader たちが書いた回答を**全部まとめて読み、問題がないかチェック**します。

具体的にチェックすること:
- **矛盾がないか**: ある質問で「多要素認証（MFA）を導入済み」と答えているのに、別の質問で「MFA は未導入」と答えていたら矛盾です
- **根拠がちゃんとあるか**: 回答に「セキュリティポリシー第3章に基づき」と書いてあるのに、実際にはそんな記述がなかったら問題です
- **確信度は適切か**: AI が「確信度: 高い」と言っているのに回答が空っぽだったら、確信度を下げます

**2層のチェック体制**があります:
1. **AI によるチェック**: 全回答をまとめて AI に渡し、矛盾や根拠不足を指摘してもらう
2. **ルールによる自動チェック**: AI のチェック結果に加えて、必ず以下のルールを適用する
   - 確信度が「低い」のに「対応済」になっている → 「回答不可」に変更
   - 回答が空なのに確信度が「高い」や「中」 → 確信度を「低い」に下げて「回答不可」に変更

AI が使えないときは、ルールベースのチェックだけで動きます。

### パート B: なぜ必要か

**Reviewer がいなくなったら？**

- **矛盾が見逃される**: Reader A と Reader B は別々に動くので、お互いの回答を知りません。矛盾した回答がそのまま提出されてしまう
- **信頼度の一貫性がなくなる**: ある Reader は甘めの判定、別の Reader は厳しめの判定をするかもしれない。横断的なチェックがなければ、信頼度がバラバラになる
- **明らかなミスが放置される**: 回答が空なのに「確信度: 高い」のまま提出されるなど、ルールベースで防げるはずのミスが通ってしまう
- **人間のレビュー負担が増大する**: すべての回答を人間が1つずつチェックすることになり、自動化の効果が半減する

### パート C: 代替手段

| 方式 | 概要 | メリット | デメリット |
|------|------|----------|------------|
| **現在の方式: LLM横断レビュー + ルールベース** | 全回答を LLM（max_tokens=8,192）でレビューし、矛盾検出・信頼度補正を実施。その上にルールベースの安全ネット（2ルール）を常に適用 | 矛盾検出や根拠チェックなど、意味的なレビューが可能。ルールベースで最低限の品質も保証 | LLM 呼び出し1回分のコスト追加 |
| **代替①: 人間が全件レビュー** | システムの出力を人間がすべてチェックする | 最も信頼性が高い | 時間とコストが膨大。質問数が多いと現実的でない |
| **代替②: ルールベースのみ** | LLM レビューなしで、確信度と回答テキストに基づく決定論的ルールのみ適用 | コストゼロ。動作が完全に予測可能 | 矛盾検出や根拠チェックができない。ルールに書かれていない問題は見逃す |
| **代替③: Reader に自己チェックさせる** | 各 Reader が回答生成時に同時にレビューも行う | 追加の LLM 呼び出しが不要 | 自分の回答を自分でチェックするため、盲点が生まれやすい。他の Reader との矛盾は検出不可 |

## 7. まとめ: 全エージェント比較表

| エージェント | LLM依存度 | LLMなしの動作 | いなくなったら | 主な代替手段 |
|---|---|---|---|---|
| **Orchestrator** | 不要 | 完全動作 | 実行順序崩壊、並列実行不可、リトライなし | シェルスクリプトで直列実行 |
| **Indexer** | オプション | ローカル抽出のみ（500文字要約） | Router の判断材料なし、トークン推定不可、更新検知不可 | ファイル名のみ / ベクトルDB |
| **Router** | オプション | 静的キーワードマッチ（12カテゴリ） | トークンコスト爆発、回答精度低下 | 固定テーブルのみ / ベクトル類似度検索 |
| **Reader** | **必須** | **動作不可** | 回答生成不可（システムの存在意義がなくなる） | RAG（将来）/ 人間が回答 |
| **Reviewer** | オプション | ルールベースのみ（2ルール） | 矛盾放置、信頼度バラバラ、明白なミス通過 | 人間が全件レビュー / ルールベースのみ |

### 補足: LLM がなくても動くエージェント

5つのエージェントのうち、**LLM が必須なのは Reader だけ**です。残りの4つは LLM がなくてもフォールバック動作します。これは意図的な設計で、LLM API が一時的に使えない場合でも、システム全体が完全に停止しないようになっています。

ただし、LLM を使うことで各エージェントの精度は大幅に向上します:
- **Indexer**: LLM 要約で FISC との関連性を含む構造化サマリーを生成
- **Router**: 質問の意味を理解した動的ルーティングで、キーワードマッチでは拾えない関連ファイルも選定
- **Reviewer**: 回答間の矛盾や根拠不足など、ルールでは表現しにくい問題を検出
